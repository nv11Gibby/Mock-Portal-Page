# Build contract for the October 2026 refinement round

Every builder in this round reads docs/REFINEMENT-BRIEF.md (the Founder's brief) and this file. The brief says what;
this file says how the pieces fit, so that work done in parallel merges cleanly.

## 1. Repository, branches, commits

* Source branch: `ihg-site`. Builders work in their own git worktree on a branch named `wave1/<key>` (or `wave2/<key>`),
  created from `ihg-site`. Commit there. The coordinator merges the branches.
* One commit per section of the brief, with a clear message in British English. No em dashes anywhere. No model names
  or tool names in commit messages. End every commit message with these two trailer lines:
  `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>` and
  `Claude-Session: https://claude.ai/code/session_01WLDTLCYMrJPXL6atw3Tdtn`.
* Before every commit run `npm run check` (syntax plus the em dash rule) and, where the page changes, the smoke test:
  `node tests/serve.js . 8765 &` then `node tests/smoke.js`. Fix what fails before committing.
* Playwright is installed globally (`NODE_PATH=$(npm root -g)` makes `require('playwright')` work; Chromium is at
  /opt/pw-browsers, never run `playwright install`). npm registry access works for small packages.
* Writing files: the shell turns `’` style escapes inside heredocs into real characters. For any file that must
  keep backslash escapes (data.js uses `’` for apostrophes), edit with the Write or Edit tool, or with Python.

## 2. Writing and content rules (from the brief, applied here)

* Keep the look. Add components in the existing visual language (serif headlines, gold hairlines, dark and light
  sections, the same spacing and motion classes). Do not restyle what exists.
* British English, plain and short. No em dashes. No invented facts: a missing fact is shown through `tbc('...')` in
  the page (it renders the amber placeholder) and written as `TO CONFIRM: ...` in code comments and docs.
* No claims of guaranteed approval, government influence, fees, prices or timelines.
* Keep `assets/js/app.js` and `assets/js/data.js` ES5 (no arrow functions, let or const, template literals, spread,
  classes). Netlify functions are modern Node (async and await are fine).
* Keep every existing form field (audience, division, routed_to, source, medium, campaign, utm_*, gclid, fbclid,
  landing, referrer, page, consent, company_url honeypot). Netlify Forms only accepts fields that also appear in the
  hidden static forms in index.html, so every new field is added there too.

### 4.3 Submission flow (frontend B, backend A)
1. Primary: POST urlencoded to `/` with `form-name` (Netlify Forms). Netlify then calls `submission-created`.
2. Fallback: if the primary POST fails (network error or non-2xx), POST JSON `{form, data}` to `config.leadEndpoint`
   (`netlify/functions/lead.js`). It runs the same core and answers `{ok:true, ref}` or `{ok:false, reason}`.
3. If both fail: show the fallback message with both office telephone numbers and the email, keep the draft in
   localStorage for every form (key `ihg-draft-<form>`), and restore it on the next visit.
4. Success state: thank you, then "Verify your phone" (only when a phone was given and the verify endpoint says it is
   enabled), then "Book a first conversation" buttons (one per office, from `config.booking`, with name, email and
   division passed as query parameters: `name`, `email`, `a1` for Calendly style links; the same parameters are
   appended to any other URL), then "Read while you wait".
5. Analytics: call `ihgTrack(name, params)` when `window.ihgTrack` exists. Names: `enquiry_submitted`,
   `phone_verified`, `booking_click`, `whatsapp_click`, `guide_download`, `quiz_completed`.

### 4.4 Phone verification (`netlify/functions/verify.js`)
POST JSON. `{action:'start', phone, email, channel:'whatsapp'|'sms'}` answers `{ok, enabled, ref}`; when Twilio is
not configured it answers `{ok:true, enabled:false}` and the page skips the step. `{action:'check', ref, phone, code,
email}` answers `{ok, verified}`. On success the backend sets the Pipedrive person field "Verification Status" to
Verified (option 982) and adds a note on the newest open lead or deal for that email; otherwise the person stays
Not Verified (983), which the core sets at creation. Env: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`,
`TWILIO_VERIFY_SERVICE_SID`. Nothing is sent without them.

### 4.6 Prerender and search (C)
* `npm run build` produces `dist/`: a copy of the site plus one HTML file per route, written twice (`about.html` and
  `about/index.html`) so every static host serves `/about`. Query-string routes are not prerendered.
* Each page has a unique `<title>`, description, `<link rel="canonical">` (no trailing slash, built from
  `config.siteUrl`), Open Graph and Twitter card tags with a real image (the page's own photo where it has one,
  otherwise `assets/img/og.jpg`), and structured data: Organization (both offices) on every page, LocalBusiness per
  office on Contact, Article for journal entries, Event for events, FAQPage on Contact, BreadcrumbList on inner pages.
* `robots.txt`, `sitemap.xml` and `journal/feed.xml` (RSS of journal entries and insights) are generated at build.
  While the site is pre-launch, robots stay `noindex` through `_headers` and the meta tag; the build has a
  `LAUNCH=1` switch that drops both. Document it.
* `_headers` is generated from `build/headers.template` with the sha256 of each inline script in index.html computed
  at build, and with the extra `script-src`, `frame-src` and `connect-src` entries that Turnstile and GA4 need only
  when those keys are configured.
* `_redirects`: keep `/netlify/*` and the old `#/` links are handled on the client (a server never sees a hash).
  Remove the catch-all rewrite so unknown paths return `404.html` with a real 404 status.
* The client app still runs on every prerendered page and takes over navigation. Add a `data-prerendered` attribute
  on `<html>` so `app.js` can skip the intro veil and reveal animations on first paint if needed.
* Preview builds: `BUILD_PREVIEW=1 npm run build` sets `data-preview` on `<html>`; the app then shows photographs
  that still lack consent (see 4.8). Production builds hide them.
* `shared/analytics.js`: reads `IHG.config.ga4`; when set, loads gtag with a cookie-free configuration
  (`client_storage: 'none'`, `anonymize_ip`, consent default denied) so no cookie notice is needed; defines
  `window.ihgTrack(name, params)` that queues until gtag is ready and sends the six conversion events.
* Core Web Vitals: hero images under 200 KB each (desktop and mobile files), fonts preloaded, width and height on
  images that affect layout, no layout shift from the header.

### 4.7 Video (D)

`{type:'video', provider:'vimeo'|'mux', id:'', poster:'<photo key>', captions:'assets/captions/<slug>.vtt', title:'',
duration:'', tbc:'Footage to be supplied'}`. Add `D.video = {hero:{...}, about:{...}}`, `events[i].video` and

poster and a `tbc()` label and no player. Captions files live in `assets/captions/` (placeholder `.vtt` with a
`TO CONFIRM` cue is fine).

### 4.8 Photo consent (D)
Every entry in `D.photos` and every event gallery photo carries `consent:true|false`. `events[i].consent:true` covers
all of that event's photographs. `photoAllowed(key)` returns true when consent is recorded, or when `<html>` has
`data-preview`. Pages that use a photograph without consent fall back to an own photo without guests (office, city
or logo mark) in production builds. The event gallery shows a short note in place of hidden photographs.
